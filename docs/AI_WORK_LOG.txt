תיעוד תהליך העבודה עם AI
===========================

מטרת המסמך: לתעד את שלבי התכנון, הבדיקה והארגון של הפרויקט. כל שינוי נבדק מול הקוד הקיים כדי לשמור על כתובות ה-API והקישורים ל-frontend.

שלב 1 - בדיקת המצב הקיים
Prompt: בדוק את מבנה הפרויקט, את קבצי package.json ואת כל נתיבי require והקישורים ל-frontend.
תוצאה: נמצאו תיקיות routes ו-services, אך לא היו תיקיות controllers, data, middleware ו-database.

שלב 2 - לימוד דרישות השיעור
Prompt: הסבר כיצד לארגן פרויקט Express לפי routes, controllers, services ו-data, בלי לשנות את הפונקציונליות.
תוצאה: routes מגדירים ניתובים, controllers מטפלים ב-req/res, services מכילים לוגיקה ו-data מטפל בנתונים.

שלב 3 - בדיקת סיכון לשבירת קישורים
Prompt: אילו קישורים עלולים להישבר אם מעבירים את db.js או setup-db.js לתיקיות אחרות?
תוצאה: צריך לעדכן require יחסיים. נשמר קובץ תאימות בנתיב הישן כאשר יש פקודות או שימושים חיצוניים.

שלב 4 - תכנון מבנה הגשה
Prompt: צור מבנה תיקיות ברור לפרויקט Node.js קיים, כולל README, תיעוד ארכיטקטורה וקובץ דוגמאות עבודה.
תוצאה: נוספו docs, README ותיאור זרימת בקשה.

שלב 5 - שמירה על אבטחת מידע
Prompt: אילו קבצים אסור להגיש בפרויקט Node.js עם PostgreSQL ו-Google Drive?
תוצאה: אין להגיש .env, google-key.json או node_modules. יש להגיש .env.example בלבד.

שלב 6 - בדיקת איכות
Prompt: אילו בדיקות בסיסיות צריך להריץ אחרי שינוי מבנה בפרויקט CommonJS?
תוצאה: להריץ node --check לקבצי JavaScript, npm start בסביבת בדיקה, ולבדוק GET /api/health.

שלב 7 - בדיקה סופית
Prompt: בדוק שהמסמכים מסבירים את המבנה ושכתובות ה-API נשארו ללא שינוי.
תוצאה: README מתעד את המבנה, ARCHITECTURE מתעד את השכבות וכתובות ה-API נשמרו.
